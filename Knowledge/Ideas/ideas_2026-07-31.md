# Idées — passe 2026-07-31

Première passe sur toute la base. Méthode SOUL.md : renversement d'hypothèses,
transfert inter-domaines, stress-test, plus petit prototype qui tranche.
Contraintes : CPU only, mémoire réduite.

## Bibliothèque de vecteurs de steering comme « compétences » portables

**Problème / hypothèse renversée** : pour spécialiser un SLM (biais vers un vocabulaire
contrôlé RAMEAU, ton de bibliothécaire de référence, format UNIMARC…), l'hypothèse par
défaut est « il faut fine-tuner ». Renversement : on ne touche pas aux poids — on stocke
le comportement comme un vecteur d'activation ajouté à l'inférence.

**Idée** : précompiler une petite collection de vecteurs de steering (un par
comportement/concept : « library », « RAMEAU », « réponds en notice courte »), chacun
pesant quelques Ko, versionnés comme des fichiers concept OKF dans `Knowledge/`. À
l'inférence on additionne le(s) vecteur(s) voulu(s) à une couche intermédiaire. La
connaissance de *comment se comporter* devient un artefact composable et inspectable,
pas un poids opaque.

**Plus petit prototype qui la prouve/réfute** : sur un modèle CPU (Qwen2.5-0.5B ou
Llama-3.2-3B), extraire un vecteur « vocabulaire contrôlé » à partir de ~50 paires de
prompts contrastifs (avec/sans concept — générables par le harnais SynthTraces, cf.
infra). Mesurer sur 20 notices test si les propositions de vedettes-matière glissent
vers des termes RAMEAU vs baseline. Une paire de fichiers : `vector.npy` + `concept.md`.

**Pourquoi ça pourrait dépasser l'existant** : coût d'entraînement nul, réversible,
composable (on additionne plusieurs vecteurs), portable et diffusable comme un package
Pi / un bundle OKF. Un « marché de comportements » plutôt qu'un zoo de modèles fine-tunés.

**Faiblesses / risques** : les vecteurs sont spécifiques à un modèle et souvent à une
couche ; l'addition de plusieurs vecteurs peut interférer (non-linéarités) ; effet plus
faible que le fine-tuning sur des tâches très structurées.

**Appuis dans la base** : `Papers/iaetbibliotheques_steering.md` (le steering, code inclus),
`synthetic_data.md` (SynthTraces pour générer les paires), `agentic.md` OKF + PI packages
(format de distribution), `llm.md` HuggingFace ecosystem (extraction CPU).

**Maturité** : implémentable — le code de steering existe déjà (billet IA&Bibliothèques) ;
le prototype tient sur un CPU en une après-midi.

## Lint frugal du wiki via propositions atomiques

**Problème / hypothèse renversée** : l'opération `Lint` de Karpathy (détecter
contradictions, pages orphelines, cross-refs manquants) reste non outillée. Hypothèse
implicite : « détecter une contradiction demande à un LLM de relire les pages entières »
(coûteux). Renversement : réduire chaque page à ses propositions atomiques, puis faire de
la comparaison d'ensembles / d'embeddings — pas de relecture globale.

**Idée** : passer chaque page de `Inspirations/` dans MPropositionneur-V2 (0.6B, CPU,
multilingue), embarquer les propositions (bge-m3), puis (a) marquer les propositions
quasi-dupliquées entre pages = redondance, (b) similarité forte + polarité opposée =
contradiction candidate, (c) page sans aucun cross-link entrant = orpheline. Sortie : un
`lint_report.md` daté.

**Plus petit prototype qui la prouve/réfute** : le lancer sur l'état actuel du repo.
Critère de succès : retrouve-t-il le doublon OKF (blog vs analyse Medium) qu'on vient de
fusionner, et signale-t-il les entrées à `### Takeaway` vide comme incomplètes ?

**Pourquoi ça pourrait dépasser l'existant** : transforme un job « LLM lit tout » en un
diff de propositions structurées, ré-exécutable en boucle (health-check planifié sur VPS),
et frugal. La bibliographie a déjà l'outil (MPropositionneur) — personne ne l'a branché sur
la maintenance d'un wiki d'agent.

**Faiblesses / risques** : qualité de l'extraction sur du markdown bruité (listes, code) ;
« polarité opposée » est heuristique — beaucoup de faux positifs à filtrer ; seuils à caler.

**Appuis dans la base** : `llm.md` MPropositionneur-V2, `kb.md` Karpathy LLM-wiki (l'op
`Lint` manquante), `claim-delta-radar` (même brique embeddings/clustering).

**Maturité** : implémentable, et directement dogfoodable sur ce dépôt — la meilleure piste
« utile tout de suite ».

## URL-swap : chaque permalien de notice devient une porte d'entrée d'agent

**Problème / hypothèse renversée** : pour offrir de l'enrichissement (résumé, propositions
atomiques, vedettes suggérées, items liés) sur un catalogue, l'hypothèse est « il faut un
nouveau portail / une nouvelle UI ». Renversement (pattern autoarxiv : `arxiv`→`autoarxiv`)
: on n'ajoute aucune interface — on détourne l'URL existante comme interface.

**Idée** : convention où l'on remplace un segment de domaine dans un permalien
(OpenAlex / HAL / SUDOC…) pour router la notice vers un agent local qui renvoie une fiche
enrichie. Zéro frontend : tout lien de notice déjà distribué devient un point d'entrée.

**Plus petit prototype qui la prouve/réfute** : micro-service CPU qui, sur un id HAL ou
OpenAlex, lit la notice (snapshot Parquet via DuckDB, ou API) et renvoie une carte
enrichie (résumé + 3 vedettes candidates via steering + items voisins). Tester sur 10
notices ; mesurer pertinence des vedettes à la main.

**Pourquoi ça pourrait dépasser l'existant** : problème de distribution résolu par le bas —
pas d'adoption d'outil à négocier, on greffe l'agent sur des URLs qui circulent déjà
(mails, biblios, pages de résultats).

**Faiblesses / risques** : réécriture d'URL = friction (extension navigateur ou service
proxy) ; couverture des identifiants hétérogène ; question d'autorité sur les vedettes
générées.

**Appuis dans la base** : `misc.md` autoarxiv, `library.md` OpenAlex snapshot + reading-papers
(raccourcis URL), `llm.md` MPropositionneur (extraction), idée steering (vedettes).

**Maturité** : plausible → implémentable ; le cœur (lecture Parquet + enrichissement) est
trivial, la partie « swap » est un vernis (proxy ou bookmarklet).

## Conseil de catalogage : fusion de logits de petits SLM spécialisés

**Problème / hypothèse renversée** : produire une notice bien formée + sujet pertinent
demanderait « un gros modèle fine-tuné cataloguage ». Renversement (fusion active de
logits, article towardsai) : trois petits modèles *intacts* votent au niveau du sampler,
sans fusion destructive des poids.

**Idée** : à l'inférence, faire voter en parallèle un modèle « format » (structure
MARC/UNIMARC), un modèle « sujet » (steeré vers RAMEAU) et un modèle « langue », en
moyennant les logits avant échantillonnage. Chaque modèle garde sa précision native ; le
routeur de logits arbitre token par token.

**Plus petit prototype qui la prouve/réfute** : fusionner deux Qwen2.5-0.5B (l'un steeré
format, l'autre vocabulaire) vs un seul modèle sur 20 notices ; mesurer validité de format
+ pertinence sujet. Trancher : la fusion bat-elle chaque modèle isolé ?

**Pourquoi ça pourrait dépasser l'existant** : pas d'entraînement, pas de merge destructif
(SLERP/mergekit dégradent), spécialisations préservées ; se combine naturellement avec les
vecteurs de steering (chaque « votant » peut être un même modèle + un vecteur différent).

**Faiblesses / risques** : **contrainte forte non dite dans l'article** — moyenner des
logits suppose un vocabulaire/tokenizer partagé ; des modèles de familles différentes ne
sont pas fusionnables ainsi. À restreindre à une même famille (variantes Qwen). Coût
mémoire = N modèles chargés (tension avec « tiny memory »).

**Appuis dans la base** : `Papers/medium_fused-tiny-local-llms.md`, idée steering, `llm.md`.

**Maturité** : intéressante → plausible ; à cadrer sur une même famille de modèles pour être
honnête.

## Radar de pilotage documentaire : claim-delta sur OpenAlex Parquet, CPU only

**Problème / hypothèse renversée** : un dashboard de pilotage suppose « des données temps
réel » (difficile en bibliothèque). Renversement : la valeur n'est pas le temps réel mais
le *delta* — ce qui émerge / disparaît entre deux fenêtres. Et un snapshot Parquet suffit,
sans cluster.

**Idée** : instancier le skill `claim-delta-radar` sur une institution réelle — diff des
propositions atomiques des résumés entre deux années — et le rendre comme artefact vivant
façon OSINT (Crucix), avec un réseau sémantique DeckGL ou une vue Keshif-plus. On voit
« claims » nouveaux / persistants / en déclin plutôt qu'un nuage statique.

**Plus petit prototype qui la prouve/réfute** : une institution, 2024 vs 2025, DuckDB avec
pushdown sur `publication_year` (skip de chunks via stats de colonnes Parquet) → extraction
propositions → clustering → 3 listes rendues en HTML. Mesurer : le delta est-il lisible et
juste pour un·e responsable de la doc ?

**Pourquoi ça pourrait dépasser l'existant** : CPU-only grâce au pushdown Parquet ; réutilise
un skill déjà écrit ; sort de la dataviz « jolie mais statique » vers un outil de décision.

**Faiblesses / risques** : qualité des résumés OpenAlex variable ; le clustering peut noyer
le signal ; « déclin » ≠ « moins important » (biais de couverture).

**Appuis dans la base** : `claim-delta-radar` (skill), `library.md` OpenAlex Parquet,
`dataviz.md` DeckGL + Keshif-plus, `misc.md` OSINT/Crucix, `llm.md` MPropositionneur.

**Maturité** : implémentable — la plupart des briques existent, reste l'assemblage + la vue.

## Anti-bibliothèque : un registre du réfuté qui nourrit la génération d'idées

**Problème / hypothèse renversée** : une base de connaissances accumule des vérités.
Renversement : ce qui a été *réfuté*, les impasses, les claims qui *disparaissent*
(claim-delta) sont aussi du signal — surtout pour un dépôt d'inventeur qui doit « ne pas
régénérer les mêmes idées ».

**Idée** : un artefact de première classe `Refuted/` (ou `dead_ends.md`) où l'on consigne
idées testées-et-cassées et hypothèses tombées, + une étape de *pré-génération* dans
`inventor-ideas` qui confronte chaque nouvelle idée à ce registre (grep + embeddings) avant
de la proposer. La base sait ce qu'elle a déjà exclu.

**Plus petit prototype qui la prouve/réfute** : créer `dead_ends.md` avec 5 impasses
connues, puis à la prochaine passe, embarquer les idées candidates et signaler celles à
distance < seuil d'une impasse. Trancher : évite-t-il au moins une redite ?

**Pourquoi ça pourrait dépasser l'existant** : la valeur d'une base d'idées se dégrade quand
elle re-propose ; mémoriser le négatif compose dans le temps et rend chaque passe plus
tranchante. Personne ne versionne ses culs-de-sac.

**Faiblesses / risques** : risque de tuer une bonne idée par ressemblance superficielle à
une impasse ; discipline de tenue du registre (même problème de fraîcheur qu'OKF).

**Appuis dans la base** : `claim-delta-radar` (claims disparaissant), `kb.md` Karpathy Lint,
et `inventor-ideas` lui-même (consigne « ne pas dupliquer les passes »).

**Maturité** : intéressante → à valeur pour la longévité du dépôt ; prototype minuscule.
