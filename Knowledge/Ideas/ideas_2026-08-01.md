## Autocomplétion de notices UNIMARC/EAD par score fondu, sans IA

**Problème / hypothèse renversée** : on suppose qu'aider un catalogueur à remplir une notice
demande un LLM ou du RAG. Renversement (Deja) : quatre features simples fondues en un score
suffisent, et le catalogue lui-même est le jeu d'entraînement.

**Idée** : reprendre les 4 signaux de Deja, transposés au catalogage — (1) correspondance
floue sur ce qui est tapé, (2) fréquence×récence des valeurs déjà employées dans ce
catalogue, (3) affinité avec le *contexte courant de la notice* (le « répertoire courant »
devient : type de document, langue, autres zones déjà remplies), (4) probabilité
d'enchaînement de zones/sous-zones (après une 200$a, quelles 7xx ; après une vedette 6xx,
quelles voisines RAMEAU). Un seul score, expliquable, hors-ligne.

**Plus petit prototype qui la prouve/réfute** : sur un dump de N notices UNIMARC existantes,
construire les 4 tables (n-grammes de valeurs, comptes, cooccurrences de zones), puis sur 20
notices tenues à l'écart, prédire la prochaine valeur de zone. Mesurer le top-3 vs une
baseline « fréquence seule ». Pur Python/DuckDB, zéro modèle.

**Pourquoi ça pourrait dépasser l'existant** : instantané, explicable (on sait *pourquoi*
telle suggestion), offline, sans hallucination ; se calibre sur l'historique local d'un
établissement plutôt que sur un modèle générique.

**Faiblesses / risques** : démarrage à froid sur zones rares ; le vocabulaire contrôlé
réclame quand même une source d'autorité ; creux pour auteurs/sujets peu fréquents.

**Appuis dans la base** : `kb.md` Deja (les 4 signaux), `llm.md` MPropositionneur (structurer
les valeurs), idée « vecteurs de steering » 2026-07-31 (fallback génératif quand la table est
creuse), `library.md` OpenAlex snapshot (source de valeurs).

**Maturité** : implémentable — le prototype tient en une journée sur un export catalogue.

## RAG sans embeddings : la pertinence comme somme de features (Deja × Graphify)

**Problème / hypothèse renversée** : « le RAG a besoin d'un modèle d'embeddings et d'une base
vectorielle ». Renversement croisé — Deja (« features fondues en un score ») + Graphify
(« la topologie du graphe EST la similarité ») : on classe les candidats sans jamais vectoriser.

**Idée** : un récupérateur qui ordonne les passages/notices par un score fondu — BM25 (flou) +
affinité de voisinage dans un graphe (communauté Leiden de l'item courant) + récence +
probabilité de cooccurrence — sans modèle d'embeddings. Le « contexte courant » (la notice ou
la requête en cours) joue le rôle du répertoire courant de Deja.

**Plus petit prototype qui la prouve/réfute** : sur `Knowledge/` (ou un jeu de notices),
comparer la récupération « score fondu » vs une récupération par embeddings (bge-m3) sur 15
requêtes ; mesurer le recouvrement des top-5 et la qualité jugée à la main. Trancher : la
version sans modèle est-elle assez proche pour s'en passer sur CPU ?

**Pourquoi ça pourrait dépasser l'existant** : entièrement CPU, explicable, maintenance
triviale (pas de ré-indexation vectorielle) ; supprime une classe entière de dépendances.

**Faiblesses / risques** : moins bon sur la similarité purement sémantique (paraphrases sans
mots partagés) ; qualité dépendante du graphe/BM25 sous-jacent ; pondération à calibrer.

**Appuis dans la base** : `kb.md` Deja + Graphify + QMD + PageFind, idée « Lint frugal »
2026-07-31, `claim-delta-radar` (comparaison honnête avec la voie embeddings).

**Maturité** : plausible → implémentable ; le bench comparatif est lui-même la livraison utile.

## Le curseur de flou comme réglage recall/precision exposé au catalogueur

**Problème / hypothèse renversée** : dans un outil de recherche/dédoublonnage, le seuil de
correspondance (distance d'édition, tolérance de translittération) est un hyperparamètre caché
choisi par le développeur. Renversement (Deja : tight/smart/loose) : en faire *un seul curseur*
visible, réglable à la volée par l'usager.

**Idée** : un matcher d'autorités (auteurs, sujets) où un cran unique de « rigueur » pilote
simultanément distance de chaîne floue, tolérance de translittération et normalisation
dates/noms — pour répondre à « cette autorité existe-t-elle déjà ? » avant d'en créer une
nouvelle. Le catalogueur arbitre lui-même recall vs precision selon le cas.

**Plus petit prototype qui la prouve/réfute** : sur un fichier d'autorités auteurs, un matcher
à 3 crans ; sur un jeu de paires étiquetées (même personne / non), tracer precision/recall à
chaque cran. Trancher : les 3 crans couvrent-ils les régimes utiles (dédoublonnage strict →
exploration large) ?

**Pourquoi ça pourrait dépasser l'existant** : déplace le compromis recall/precision du code
vers l'interaction — un choix de design, pas seulement un algo. Réduit les faux doublons
d'autorités, plaie connue des catalogues.

**Faiblesses / risques** : nécessite un jeu étiqueté pour calibrer les crans ; risque de
sur-confiance de l'usager dans le cran « loose ».

**Appuis dans la base** : `kb.md` Deja (le curseur), idée « autocomplétion de notices » (même
socle de features), `library.md` (fichiers d'autorité).

**Maturité** : intéressante → à valeur ; petit prototype, fort impact qualité sur les autorités.

# Passe 2 — 2026-08-01 (déclencheur : AirLLM / Kimi K3 sur GPU 4 Go)

Angle donné par l'utilisateur : combiner l'inférence couche-par-couche d'AirLLM avec les
HF buckets pour le stockage. + idées extraites.

## Inférence AirLLM avec shards de couches en stockage objet (HF buckets / hf-mount)

**Problème / hypothèse renversée** : servir un très grand modèle réclame de la VRAM — et même
avec AirLLM, il faut ~140 Go+ de shards sur le disque local. Renversement : le « disque »
d'AirLLM peut être un stockage objet distant, partagé et versionné (HF buckets / hf-mount).

**Idée** : pointer `layer_shards_saving_path` vers un montage hf-mount (ou streamer les shards
depuis un repo HF), et précharger la couche N+1 pendant le calcul de N pour masquer la latence
réseau. On sépare *stockage* (illimité, mutualisé, versionné HF) et *compute* (n'importe quel
petit nœud CPU/4 Go). Un parc de petits nœuds sert alors un modèle géant depuis un stockage commun.

**Plus petit prototype qui la prouve/réfute** : un 70B, shards sur HF, montés via hf-mount ;
mesurer tokens/s avec prefetch on/off vs disque local. Trancher : le réseau tue-t-il le débit,
ou le prefetch le masque-t-il assez pour un usage batch/offline ?

**Pourquoi ça pourrait dépasser l'existant** : découple capacité et matériel ; mutualise un seul
jeu de poids entre nœuds ; s'appuie sur des briques déjà notées (hf-mount, HF buckets, `layer_shards_saving_path` natif d'AirLLM).

**Faiblesses / risques** : I/O réseau ≫ disque local → latence par token élevée ; adapté à
l'inférence batch/asynchrone, pas au temps réel ; coûts d'egress.

**Appuis dans la base** : `llm.md` AirLLM + HuggingFace ecosystem/hf-mount, `agentic.md` HF moonbot (HF Buckets comme mémoire).

**Maturité** : plausible → implémentable ; les deux briques existent, le proto est un branchement.

## MoE × AirLLM : ne streamer que les experts routés

**Problème / hypothèse renversée** : AirLLM naïf charge *toutes* les couches à chaque token.
Pour un MoE (Kimi K3 : 2.8T total, faible actif ; Inkling-Small : 276B/12B), c'est du gâchis :
seuls quelques experts sont activés par token.

**Idée** : coupler le routeur MoE au chargement paresseux — précharger uniquement les experts
prédits pour le token courant, sauter les autres. L'E/S (le vrai goulot d'AirLLM) chute d'un
facteur proportionnel à la sparsité du routage.

**Plus petit prototype qui la prouve/réfute** : sur un petit MoE (type Mixtral), mesurer le
volume d'E/S « tous experts » vs « experts routés » et l'effet sur le débit. Trancher : le
gain d'E/S dépasse-t-il l'overhead de décision + cache miss ?

**Pourquoi ça pourrait dépasser l'existant** : MoE + streaming est un mariage naturel jamais
exploité ensemble ; rend le streaming disque viable pour les modèles frontière (qui sont MoE).

**Faiblesses / risques** : routage dynamique → cache miss, prefetch difficile ; experts partagés
chauds à garder en cache ; gains dépendants de la sparsité réelle.

**Appuis dans la base** : `llm.md` AirLLM, `llm-training.md` Inkling-Small (MoE), idée précédente.

**Maturité** : intéressante → plausible.

## Streamer le KV-cache comme AirLLM streame les poids

**Problème / hypothèse renversée** : AirLLM applique « un à la fois » aux *poids*. Mais sur
petit matériel, c'est souvent le *KV-cache* d'un long contexte (1M tokens) qui explose la mémoire,
pas les poids.

**Idée** : appliquer la même bascule au KV-cache — pagination sur disque/objet, on charge les
segments de contexte pertinents, on calcule, on libère (cf. Memory Caching : checkpoints
compressés aux frontières de segments). Utile pour lire de longs documents patrimoniaux sur CPU.

**Plus petit prototype qui la prouve/réfute** : un KV-cache paginé sur disque pour un petit
modèle ; mesurer mémoire vs latence sur contexte long (ex. 200k tokens). Trancher : l'éviction
coûte-t-elle moins que l'attention pleine ?

**Pourquoi ça pourrait dépasser l'existant** : déplace la frugalité de la dimension *poids* vers
la dimension *contexte* — la vraie contrainte pour la lecture de longs corpus.

**Faiblesses / risques** : I/O ; politique d'éviction non triviale ; recouvrement calcul/chargement
plus dur que pour des couches à ordre fixe.

**Appuis dans la base** : `llm.md` AirLLM + World models, `Papers/medium_llm-rnn.md` (Memory Caching).

**Maturité** : intéressante.
